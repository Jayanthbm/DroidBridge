# P03 — Local transport and pairing

**Status: protocol layer implemented and verified; the live session is not.** The two pieces of P03
that carry the real risk — length-prefixed framing and the short authentication code — are built,
tested, and proven identical across Kotlin and Swift. The TLS session, discovery wiring and
reconnect behaviour are not built, so none of P03's six acceptance criteria are met yet.

## What was built

**`shared/protocol/session/Framing.kt`** — `[4-byte big-endian length][payload]` per ADR-012.

The length prefix is attacker-controlled, so it is validated **before anything is allocated**. A
peer announcing 2 GiB is rejected on the header alone: the reader does not block waiting for a
payload that will never arrive, and does not reserve memory for it. `FrameReader` is structured so
there is no code path that allocates from an unvalidated length.

Two decisions worth naming:

- The prefix is decoded as **unsigned**. A 4-byte signed read turns `0xFFFFFFFF` into `-1`, and
  every `> max` check then passes. That single detail is the difference between a bound and the
  appearance of one.
- A reader that hits a framing error **latches failed** and refuses every later feed.
  Resynchronising after a framing error is how a decoder silently starts interpreting payload bytes
  as headers, so the only correct response is to close the connection.

`MAX_CONTROL_PAYLOAD_BYTES` is 1 MiB, sized from the largest legitimate control message rather than
picked for tidiness: `mirror.format` carries Base64 SPS/PPS (a few KiB) and `clipboard.text` carries
up to the P04 100 KiB cap. Media has its own transport (ADR-027), so this limit never has to
accommodate a video frame.

**`shared/protocol/session/ShortAuthenticationCode.kt`** and **`macos/Core/ShortAuthenticationCode.swift`**
— the code both screens display during pairing (ADR-011, NETWORK_PROTOCOL §3).

- Inputs are **sorted by content**, so both sides derive the same code without agreeing who is
  "first". A role-based order would let a peer choose the role that produces the code it prefers.
- Each identity is **length-prefixed** before hashing. Without it, `("ab","c")` and `("a","bc")`
  both concatenate to `"abc"`, and an attacker controlling one identity could pick a key pair that
  yields a target code.
- The code is a **confirmation value, not a secret**. It is derived from public keys, so anyone
  observing both can compute it. Its only job is to let a human notice a substitution;
  confidentiality comes from TLS.
- Modulo bias is real but negligible (2^32 is not a multiple of 10^6, so the first 967,296 values
  appear one extra time, about 0.02%). Stated in the code rather than left for a reader to wonder
  about.

## Verified

**64 shared protocol tests pass** (up from 31), including 20 framing tests and 14 SAS tests.

Framing, specifically:

- a length prefix round-trips and is big-endian on the wire;
- `0xFFFFFFFF` decodes to `4294967295`, not `-1`;
- an oversized header is rejected **without waiting for the payload**;
- a failed reader stays failed and refuses a subsequent valid frame;
- a frame split across reads one byte at a time is reassembled;
- several frames in one chunk are emitted in order;
- a trailing partial frame is held until completed;
- all 256 byte values round-trip unchanged (payloads are binary, not text);
- the limit itself is accepted and one past it is not.

**19 macOS tests pass**, including **cross-language agreement**.

### The cross-language check is the important one

The Mac is Swift and the Android side is Kotlin, so the SAS algorithm exists twice. That is exactly
the duplication that drifts silently: if the two disagree, a real pairing shows two different codes
and the user rejects a valid device with no way to tell why.

Six fixed vectors are generated by `VectorPrinter` in `shared/protocol` and asserted in
`macos/Tests/ShortAuthenticationCodeTests.swift`. The Swift test does not recompute its own
expectation — a test that derived its own answer would agree with itself. Both implementations
produce identical codes for all six, including the zero-padded case (`075101`) and the
length-ambiguity pair (`144752` vs `297114`).

To regenerate the vectors after any change:

```bash
cd shared/protocol && ./gradlew test --tests "*VectorPrinter*" -i | grep VECTOR
```

## Not built, and why

- **TLS 1.3 with pinned certificates.** Needs the identity generation and the Android
  `network_security_config.xml` anchor (ADR-011, ADR-024), and the handshake cannot be exercised
  without a working peer — which P02 blocks.
- **Discovery wiring.** Depends on the winning P02 path, which is unresolved.
- **Reconnect after Wi-Fi drop.** Needs a live session.
- **Rate limiting, idle timeout, replay protection.** Specified in NETWORK_PROTOCOL §4, not
  implemented.

## P03 acceptance criteria — none met yet

| Criterion | Status |
|---|---|
| Unknown peer rejected | not met — no handshake |
| Wrong code rejected | **partially**: the code derivation and comparison are tested, but nothing enforces rejection in a session |
| Tampered message rejected | **partially**: framing rejects malformed and oversized frames; no integrity check exists yet (that is TLS's job) |
| Session closes on network loss | not met — no session |
| No cloud connection | not met — nothing to monitor yet |
| Reconnect after Wi-Fi drop | not met — no session |

The two partial rows are honest partials: the primitives are proven, the enforcement is not built.

## Blockers

P03's remaining work needs a live peer, which needs P02. P02 is blocked twice over: the picker path
requires Android 17 (`android.net.nsd.DiscoveryRequest` exists only in the API 37 platform), and
Bonjour does not publish from this Mac. Both are recorded in `P02-local-networking.md`.

The framing and SAS work was deliberately chosen because it is the part of P03 that can be proven
without a peer, and it is where the security-relevant bugs live.
