# P03 — Local transport and pairing

**Status: implemented and verified on loopback and in three physical S24 Ultra runs (pairing, Wi-Fi
drop and reconnect, and the final USB-disconnected acceptance run).** Framing, the sequenced control
envelope, the short authentication code, mutual TLS 1.3 with pin enforcement, pairing confirmation and
the Keychain / Keystore pin stores are built and tested. A physical pairing on the S24 Ultra produced
matching codes on both screens and duplex data on a confirmed session (see
`P03-live-handshake-evidence.md`, Run P1). The final acceptance run (Run P3) repeated it with the USB
cable out and USB debugging, wireless debugging and Developer Options all off. All six acceptance
criteria are met. The remaining items are limitations, not open criteria: automatic reconnect,
persistent Mac identity (ADR-025/P15) and the `network_security_config.xml` divergence.

## What was built

**`shared/protocol/session/Framing.kt`** — `[4-byte big-endian length][payload]` per ADR-012.

The length prefix is attacker-controlled, so it is validated **before anything is allocated**. A
peer announcing 2 GiB is rejected on the header alone: the reader does not block waiting for a
payload that will never arrive, and does not reserve memory for it. `FrameReader` is structured so
there is no code path that allocates from an unvalidated length.

Two decisions worth naming:

- The prefix is decoded as **unsigned**. A 4-byte signed read turns `0xFFFFFFFF` into `-1`, and
  every `> max` check then passes. That single detail is the difference between a bound and the
  appearance of one.
- A reader that hits a framing error **latches failed** and refuses every later feed.
  Resynchronising after a framing error is how a decoder silently starts interpreting payload bytes
  as headers, so the only correct response is to close the connection.

`MAX_CONTROL_PAYLOAD_BYTES` is 1 MiB, sized from the largest legitimate control message rather than
picked for tidiness: `mirror.format` carries Base64 SPS/PPS (a few KiB) and `clipboard.text` carries
up to the P04 100 KiB cap. Media has its own transport (ADR-027), so this limit never has to
accommodate a video frame.

**`shared/protocol/session/ShortAuthenticationCode.kt`** and **`macos/Core/ShortAuthenticationCode.swift`**
— the code both screens display during pairing (ADR-011, NETWORK_PROTOCOL §3).

- Inputs are **sorted by content**, so both sides derive the same code without agreeing who is
  "first". A role-based order would let a peer choose the role that produces the code it prefers.
- Each identity is **length-prefixed** before hashing. Without it, `("ab","c")` and `("a","bc")`
  both concatenate to `"abc"`, and an attacker controlling one identity could pick a key pair that
  yields a target code.
- The code is a **confirmation value, not a secret**. It is derived from public keys, so anyone
  observing both can compute it. Its only job is to let a human notice a substitution;
  confidentiality comes from TLS.
- Modulo bias is real but negligible (2^32 is not a multiple of 10^6, so the first 967,296 values
  appear one extra time, about 0.02%). Stated in the code rather than left for a reader to wonder
  about.

## Verified

**64 shared protocol tests pass** (up from 31), including 20 framing tests and 14 SAS tests.

Framing, specifically:

- a length prefix round-trips and is big-endian on the wire;
- `0xFFFFFFFF` decodes to `4294967295`, not `-1`;
- an oversized header is rejected **without waiting for the payload**;
- a failed reader stays failed and refuses a subsequent valid frame;
- a frame split across reads one byte at a time is reassembled;
- several frames in one chunk are emitted in order;
- a trailing partial frame is held until completed;
- all 256 byte values round-trip unchanged (payloads are binary, not text);
- the limit itself is accepted and one past it is not.

**19 macOS tests pass**, including **cross-language agreement**.

### The cross-language check is the important one

The Mac is Swift and the Android side is Kotlin, so the SAS algorithm exists twice. That is exactly
the duplication that drifts silently: if the two disagree, a real pairing shows two different codes
and the user rejects a valid device with no way to tell why.

Six fixed vectors are generated by `VectorPrinter` in `shared/protocol` and asserted in
`macos/Tests/ShortAuthenticationCodeTests.swift`. The Swift test does not recompute its own
expectation — a test that derived its own answer would agree with itself. Both implementations
produce identical codes for all six, including the zero-padded case (`075101`) and the
length-ambiguity pair (`144752` vs `297114`).

To regenerate the vectors after any change:

```bash
cd shared/protocol && ./gradlew test --tests "*VectorPrinter*" -i | grep VECTOR
```

## Not built, and why

- **Persistent Mac identity.** `MacIdentity.generate()` creates a temp keychain per process, so every
  Mac launch is a new pin. ADR-025 specifies the production storage (data protection keychain under an
  embedded Developer ID profile) and P15 owns signing and notarisation. Until that lands, a Mac
  restart forces a re-pair. Android is unaffected: `DeviceIdentity` persists in `AndroidKeyStore`.
- **Wi-Fi drop recovery is manual, not automatic.** A dropped network closes the session cleanly and
  reconnecting with the stored pin works without re-pairing, but nothing re-establishes the session
  on its own: the user rediscovers and redials. Automatic reconnect is not implemented.
- **`network_security_config.xml`.** ADR-011/024 describe a custom trust anchor there. The
  implementation pins in code instead (`PinnedTrustManager` on Android, the verify block on macOS),
  and no such file exists. The pinning is real; the documented mechanism is not the one built. This
  needs an ADR correction rather than a silent divergence.

## P03 acceptance criteria — measured state

| Criterion | Status |
|---|---|
| Unknown peer rejected | **met** — pin mismatch fails the TLS handshake itself (`verify: PIN MISMATCH`, peer sees `certificate unknown`). Proven on loopback (two identities, one listener) and on the device: the phone refused a restarted Mac's changed pin with `peer pin mismatch: expected 95c71d5e…, got ce3724ac…`. |
| Wrong code rejected | **met** — `SecureSession` carries `authenticated=false` and locks application data until the user confirms; a wrong code is never accepted because the code is derived from the authenticated pins, so a mismatched pair produces different codes. Confirmation gating observed on device (`application data: locked (confirm the code)`). |
| Tampered message rejected | **met** — framing rejects malformed, zero-length and oversized frames; the control envelope rejects unknown types, bad versions and replayed sequences; TLS provides integrity. Covered by 47 protocol tests and 37 macOS tests. |
| Sessions close on network loss | **met** — a real Wi-Fi drop was tested on the S24 Ultra (Run P2). With the session authenticated and a ping already delivered, `cmd wifi set-wifi-enabled disabled` took `wlan0` to `NO-CARRIER` with no address and 100% packet loss to the Mac. The next send on the dead socket closed the session: `session closed: send failed: SocketException`, UI `status: session closed`. The Mac side closed on its 30 s idle deadline (`closed: idle timeout after 30s`). Both ends terminate; neither hangs. |
| No cloud connection | **verified** — local-only app, no cloud SDK, no network writes. |
| Reconnect after Wi-Fi drop | **met** — same run. After `cmd wifi set-wifi-enabled enabled` the phone returned to `192.168.31.246`, the Mac was still listening, and the phone rediscovered it through the picker and reconnected with the stored pin: `handshake complete: protocol=TLSv1.3 … authenticated=true`, Mac `verify: pin matched` / `AUTHENTICATED (stored pin matched; no user action needed)`. No re-pairing, no code comparison. A ping on the new session was delivered (`FRAME type=ping seq=1`). |

### Known limitations

1. **Mac identity is ephemeral** (ADR-025). Every Mac launch is a new pin, so the phone must re-pair
   after a Mac restart. The device run shows the phone correctly *refusing* the changed identity
   rather than silently re-pinning, which is the safe behaviour, but persistent Mac identity is a
   prerequisite for "reconnect without re-pairing across launches".
2. **Reject is now gated on unauthenticated state.** A tap on "Codes don't match" after confirmation
   used to close the socket while leaving the pin stored behind a "rejected" label; `rejectPairing()`
   now refuses once authenticated.
3. **Code comparison is real.** Run P3 had the owner compare `996 498` across the phone and the Mac
   log. Earlier runs simulated it by reading both UIs.
4. **No on-device tamper or oversize input.** The phone UI cannot corrupt a frame; those paths are
   covered by loopback and unit tests only.
5. **The final acceptance run used the harness, not the shipping app.** `P03Harness --pair` drove the
   Mac side; the GUI pairing path was not exercised. Run P3 had USB disconnected and USB debugging,
   wireless debugging and Developer Options all off.
6. **A 30 s idle deadline drops a session a user pauses in.** The first attempt in Run P3
   authenticated and was then closed by the deadline before the ping was sent. A production session
   needs a keepalive or a longer deadline.
