# P16 — BLE HID keyboard feasibility

**Status:** The POC initially failed service publication with `The specified UUID is not allowed for this operation` (user-reported 2026-11-20). It now registers SIG UUIDs in canonical Bluetooth-base form and includes the HOGP-required Battery Service and Device Information Service (including PnP ID) before adding HID. Review of Apple's public CoreBluetooth header also found that `CBMutableDescriptor` supports only User Description and Presentation Format custom descriptors; CoreBluetooth creates CCCDs automatically, but does not publicly support HID Report Reference `0x2908`. The POC therefore tests the fixed Boot Keyboard protocol only and deliberately does not claim Report Protocol support. Build and strict signature verification pass; Mac-side service publication still needs a manual retest. On the OnePlus, the already-bonded row tap left the host disconnected with no input device; the last Mac status was not subscribed, and no key was sent. S24 behavior is unknown. P17 Classic HIDP remains separate.

## Scope

- Test only whether the Mac can appear as a standard BLE HID keyboard and deliver fixed arrow-key press/release reports to a focused, purpose-built Android receiver.
- This is isolated feasibility code, not a production feature. It does not establish pointer, text entry, touch gestures, general app control, mirroring or clipboard behavior.
- No Accessibility Service/API, event tap, global input capture, hidden API, Android Bluetooth permission, ADB-generated functional input or protected-screen interaction.
- During development setup only, ADB may install/launch the receiver, open Bluetooth Settings, and connect/reconnect an already-paired test peripheral. For first pairing, the owner visually checks that the code matches before confirming; ADB must not accept an unverified pairing code. Observe key delivery on the phone display. Never use ADB to send the test key, capture pixels/UI hierarchy, or read/write clipboard content. Final acceptance uses USB disconnected with both debugging modes off.

## Standards, platform limitation, and reference attribution

- Bluetooth SIG [HID over GATT Profile 1.2](https://www.bluetooth.com/wp-content/uploads/Files/Specification/HTML/hogp_v1-2_1777405843/HOGP_v1.2/out/en/index-en.html) requires the HID, Battery, and Device Information services; the Device Information service includes a mandatory PnP ID. HID includes Battery only when Battery Level appears in the Report Map; this keyboard does not use Battery Level as a report, so Battery remains a separate primary service. It defines separate mutually exclusive Boot Host and Report Host procedures. The Report Host requires Report Map and Report characteristics with Report Reference descriptors; the Boot Host uses the fixed Boot Keyboard input report and selects Boot Protocol using Protocol Mode. The HID Service itself still requires a readable Report Map, which this POC publishes; Boot Hosts ignore it. The optional Boot Host route is not evidence that the OnePlus or S24 supports it.
- Apple's public [CoreBluetooth SDK header `CBDescriptor.h`](https://developer.apple.com/documentation/corebluetooth/cbmutabledescriptor) states that local mutable descriptors support only Characteristic User Description and Characteristic Presentation Format; Extended Properties and Client Characteristic Configuration are created automatically from the characteristic properties. That public API cannot construct HOGP Report Reference `0x2908`, so the POC publishes no Report characteristics and does not implement HOGP Report Protocol.
- Reference reviewed, and a separate isolated reference-derived comparison was later created from [`jqssun/darwin-bt-remote`](https://github.com/jqssun/darwin-bt-remote), commit [`e64cae983b8816e7e2f067e79025ffc49faf7e2d`](https://github.com/jqssun/darwin-bt-remote/tree/e64cae983b8816e7e2f067e79025ffc49faf7e2d), especially [`GATT.swift`](https://github.com/jqssun/darwin-bt-remote/blob/e64cae983b8816e7e2f067e79025ffc49faf7e2d/BTHIDKit/Sources/BTHIDKit/LowEnergy/GATT.swift) and its [`AGPL-3.0-only` license](https://github.com/jqssun/darwin-bt-remote/blob/e64cae983b8816e7e2f067e79025ffc49faf7e2d/LICENSE). The original P16 remains independent and Boot-only. The comparison lives only under `macos/Experiments/P16BLEHIDReference/`, includes the upstream license and in-app attribution, excludes Classic HIDP, Accessibility/Direct Input and the upstream service-changed workaround, and has not been device-tested. It is local isolated research while the AGPL handling is reviewed; do not copy it into production, push, share or otherwise convey it until the owner resolves the license position. Private personal use does not itself create a distribution obligation under AGPL's network-source clause, which concerns users interacting remotely with a modified version; sharing/distribution or offering a modified version as a network service warrants license review.

The linked reference repository's `GATT.swift` instead registers canonical Bluetooth-base UUIDs (for example `00001812-0000-1000-8000-00805F9B34FB`) and keeps the short form only for advertising. We applied that UUID-format distinction independently to P16, including descriptors. This is a plausible cause, not yet a verified fix: the updated app has built and passed strict signature verification, but service publication has not been manually retried. A custom/non-SIG UUID remains invalid as a HID workaround. No Android pairing or input test has occurred.

## Results / acceptance

**NO-GO for macOS BLE HOGP toward Android (2026-11-20, OnePlus Nord AC2001 / Android 12 / API 31).** Android bonds the Mac but never binds it as a HID input device. `HidHostService` still reports no input devices (`mInputDevices:` empty, `mTargetDevice: null`) and the Mac receives **zero** GATT reads, writes or subscriptions. This result was reproduced identically with **two independent implementations**: the project's own P16 POC, and the **unmodified** upstream `darwin-bt-remote` app in its default BLE mode (Mac log showed only `CB state -> 5` and `advertising as BTRemote`, then nothing). The mechanism is host-side classification, not a GATT layout defect: the Mac advertises on its public address `60:3E:5F:31:D0:6D`, which is also its BR/EDR address, so Android lists the peer as `[ DUAL ]` and routes HID over Classic BR/EDR instead of HOGP. No Report Map, descriptor, Report Reference or protocol change can alter that routing; the same Mac succeeds over Classic HIDP, which is why [P17](P17-classic-hidp.md) now carries the Mac→Android input path. Do not spend further effort on BLE HOGP for Android; keep P16 as the record of this negative result.

**Acceptance remains pending for the earlier Boot-only retest.** Canonical UUID registration, the required Battery/Device Information services, and the mandatory read-only Report Map are implemented, but the Mac UI has not yet been manually exercised after the profile correction. The public CoreBluetooth descriptor API does not support HID Report Reference, so this POC is explicitly Boot Protocol only. On 2026-11-20, the Android 12 OnePlus was tested over Wi-Fi ADB while the owner reported advertising; the bonded entry remained disconnected and no LE connection attempt or HID input device was observed. The later A/B run with the unmodified upstream BLE app confirmed this is an Android host-classification limit rather than a P16 defect: the phone bonded as `[ DUAL ]`, `HidHostService.mInputDevices` stayed empty, and the Mac side logged no GATT activity at all. Receiver counters remained zero and no key was sent over BLE. The S24 Ultra has no P16 evidence. If Boot Protocol does not connect or subscribe, record the exact result and stop—do not add undocumented APIs. P17 Classic HIDP remains independent and pending. No pointer control, touch-equivalent gestures, text entry, clipboard synchronization, protected-app behavior or full remote control is established.
